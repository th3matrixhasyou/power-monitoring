# Infrastructure Power Monitoring

A containerized infrastructure monitoring stack built according to **Infrastructure as Code (IaC)** principles.

The project is designed for centralized monitoring of operating system availability, server hardware health, and power consumption of servers and workstations.

## 🏗 Architecture

The monitoring stack consists of the following components:

| Component | Description |
|---|---|
| **Prometheus** | Collects, stores, and processes time-series data (TSDB). |
| **Blackbox Exporter** | Checks operating system availability using ICMP. |
| **IPMI Exporter** | Collects hardware metrics from Huawei and Lenovo servers via IPMI 2.0 (LAN 2.0). |
| **Node Exporter** | Collects system metrics and reads custom metrics via `textfile_collector`. |
| **Custom Power Collector** | Bash script `get_power.sh` for collecting power consumption data via DCMI and IPMI SDR. |
| **Grafana** | Provides metric visualization and infrastructure status monitoring. |

All components are deployed in Docker containers using Docker Compose.

Prometheus, Grafana, and other component configurations are stored in a Git repository. Grafana dashboards are managed via JSON Provisioning.

## 🔌 Power Monitoring (IPMI / DCMI)

Due to differences in BMC implementations across various hardware vendors (Huawei TaiShan, Lenovo XCC, etc.), the standard IPMI Exporter does not always provide accurate power consumption readings in Watts.

In particular, some implementations may return zero values or readings from individual redundant power supplies, which do not reflect the actual power consumption of the entire system.

To solve this issue, a custom metric collection mechanism was implemented — `get_power.sh`.

The script uses a hybrid polling algorithm, automatically selecting the appropriate method for data retrieval.

### Data Collection Algorithm

**1. DCMI (Data Center Manageability Interface)**

First, the script runs the following command:

```bash
ipmitool dcmi power reading
```

DCMI provides a single instantaneous power consumption value for the entire system (`Instantaneous power reading`).

This is the preferred method for servers that support the corresponding DCMI implementation.

**2. IPMI SDR (Sensor Data Record)**

If DCMI is not supported, does not return valid data, or reports zero power consumption, the script switches to an alternative method:

```bash
ipmitool sdr list full
```

After this, the following operations are performed:

- Fetching the full list of hardware sensors.
- Searching for power-related sensors.
- Filtering out zero values.
- Selecting valid readings to generate metrics.

This approach allows accounting for firmware differences across various vendors and obtaining more accurate power consumption data.

### Forwarding Metrics to Prometheus

The results generated by `get_power.sh` are written to a file:

```text
textfile_data/ipmi_power.prom
```

Node Exporter reads this file using `textfile_collector` and passes the collected metrics to Prometheus.

This allows monitoring power consumption independently of the main IPMI Exporter.

## ➕ Adding New Servers

Adding new hardware is done through the Prometheus configuration.

Regardless of the server vendor and the supported power monitoring method (DCMI or IPMI SDR), the server addition procedure remains the same.

**The power data collection protocol is automatically selected by the `get_power.sh` script.**

### Step 1. Adding Monitoring Targets

Open the following file:

```text
prometheus/prometheus.yml
```

For each new server, you need to add two monitoring targets:

- To `icmp_ping_servers` — the operating system IP address.
- To `ipmi_servers` — the iBMC interface IP address.

Example:

**ICMP — OS availability check:**

```yaml
- targets:
    - '192.168.0.255'
  labels:
    hostname: 'g10-newserver'
    rack: 'g10'
    team: 'Cloud'
```

**IPMI — hardware components monitoring via iBMC:**

```yaml
- targets:
    - '192.168.0.254'
  labels:
    __param_module: 'ibmc_192_168_0_254'
    hostname: 'g10-newserver'
    rack: 'g10'
    team: 'Cloud'
```

> **Important:** Keep the required label structure: `hostname`, `rack`, `team`, and `__param_module`. These labels are used by the monitoring configuration and the `get_power.sh` script to identify hardware and group metrics by racks in Grafana.

### Step 2. Adding iBMC Credentials

Add the new server's credentials to the IPMI Exporter configuration.

To do this, decrypt `ipmi.yml.enc` into RAM, make the necessary changes, and encrypt the file back.

Detailed instructions are provided in the [Security Management](#-security-management) section.

### Step 3. Applying Changes

After updating the configuration, run:

```bash
./deploy.sh
```

The script will prepare the configuration and apply the changes to the containers.

## 🤖 Automated Host Management (manage_host.sh)

To avoid errors during manual YAML editing and OpenSSL operations, an interactive `manage_host.sh` script has been added to the project. It fully replaces the routine steps from the "Adding New Servers" section.

### Script Features:
- **Interactive input:** Prompts for IP addresses, hostname, team, and provides a rack selection from an automatically gathered list.
- **Secure password handling:** Prompts for the iBMC password with confirmation, independently decrypts `ipmi.yml.enc`, adds the credentials, and encrypts the file back without leaving traces on the disk.
- **Syntax error protection:** Strictly maintains indentation when adding targets to `prometheus.yml`.
- **Smart removal:** Allows safely cutting out hosts from the configuration by their `hostname`.
- **Hot reload:** After adding or removing, the script automatically restarts the necessary containers (`prometheus` and `ipmi-exporter`) for instant change reflection in Grafana.

To run the script (Docker permissions required):

```bash
sudo ./manage_host.sh
```

## 🚀 Deployment

To deploy the stack on a new host, follow these steps:

**1. Clone the repository:**

```bash
git clone <repository-url>
cd <repository-directory>
```

**2. Prepare the deployment script:**

```bash
chmod +x deploy.sh
```

**3. Run the deployment:**

```bash
./deploy.sh
```

During execution, the script will prompt for the master password to decrypt the iBMC configuration.

Decrypted credentials are passed when preparing Docker Secrets without creating a persistent plaintext file on the SSD.

In addition to the basic container launch, the `deploy.sh` script automatically:
- Sets up a task in `cron` to execute `get_power.sh` every minute (ensuring power consumption collection).
- Waits for Grafana to be fully ready and automatically creates a `monitoring` user (view-only) via REST API.

## 🔐 Security Management

### iBMC Credentials Protection

Credentials are protected with OpenSSL AES-256-CBC encryption using PBKDF2.

The plaintext `ipmi.yml` file is not stored in the Git repository and must not be saved on persistent storage.

The encrypted configuration is located at the following path:

```text
ipmi/ipmi.yml.enc
```

For configuration editing (if you opt out of using `manage_host.sh`), temporary storage in Linux RAM is used — `/dev/shm`.

### 1. Viewing Configuration

To view the contents of the encrypted file without saving a decrypted version to disk, run:

```bash
openssl enc -aes-256-cbc -d -salt -pbkdf2 \
  -in ipmi/ipmi.yml.enc
```

OpenSSL will prompt for the master password and output the decrypted contents directly to the terminal.

### 2. Editing Credentials

**Step A. Decrypt to RAM**

```bash
openssl enc -aes-256-cbc -d -salt -pbkdf2 \
  -in ipmi/ipmi.yml.enc \
  -out /dev/shm/ipmi-edit.yml
```

Enter the master password.

**Step B. Edit configuration**

```bash
nano /dev/shm/ipmi-edit.yml
```

Add a new iBMC module or update existing credentials.

**Step C. Re-encrypt the updated file and save to SSD**

```bash
openssl enc -aes-256-cbc -salt -pbkdf2 \
  -in /dev/shm/ipmi-edit.yml \
  -out ipmi/ipmi.yml.enc
```

(Enter and confirm the master password.)

**Step D. Destroy the plaintext file from RAM (CRITICAL)**

```bash
rm -f /dev/shm/ipmi-edit.yml
```

After completing the procedure:

1. Make sure the encrypted file `ipmi.yml.enc` is updated.
​2. Commit changes to Git.
3. Run `./deploy.sh` to apply the updated configuration.

> **Important:** `/dev/shm` uses a temporary file system located in RAM. This reduces the risk of saving plaintext credentials to the SSD, but does not guarantee the complete absence of traces in the swap file, memory dumps, or system logs. For additional protection, it is recommended to disable swap or use an encrypted swap, as well as restrict access to the monitoring processes.

## 📊 Grafana Dashboards Management

Grafana dashboards are managed via JSON Provisioning and stored in the Git repository.

Main dashboard file:

```text
grafana/dashboards_json/nlrc_custom.json
```

Changes must be made via Git to ensure configuration safety and the ability to restore dashboards after container recreation.

### Dashboard Update Procedure

**1.** Open the required dashboard in the Grafana web interface.

**2.** Make the necessary changes.

**3.** Export the updated dashboard in JSON format.

**4.** Replace the file contents:

```text
grafana/dashboards_json/nlrc_custom.json
```

**5.** Commit changes to Git:

```bash
git add grafana/dashboards_json/nlrc_custom.json
git commit -m "Update Grafana dashboard"
git push
```

Grafana automatically detects changes to JSON files through the configured Provisioning mechanism with a check interval of 10 seconds.

> **Important:** Do not use the Grafana web interface as permanent configuration storage. The Git repository is the Single Source of Truth.
